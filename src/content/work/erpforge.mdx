## The Thesis Test

[Sample ERP](/work/sample-erp) proved a product leader with the right process can direct AI tools to build a system that holds to real architectural discipline. But the rigor lived in *me*: the discovery questions I knew to ask, the order I asked them in, the judgment calls translating answers into architecture decisions.

ERPForge is the harder question: can that judgment be codified into reusable AI skills, so the next custom system builds faster than the last, and the one after that faster still? If yes, the skills become the product. The ERP is just what they produce.

I think of this as trying to build a software factory: not one custom ERP, but a repeatable line that takes a specific business's requirements in one end and turns out working software on the other, without a systems integrator standing in the middle for months. A factory doesn't get slower as it makes more units. The test is whether custom software delivery can work the same way.

## The Problem

Traditional ERPs exist because code was expensive. Vendors built lowest-common-denominator software for a business segment, then tried to configure it per customer. Big customers got the most features. Small ones got the base package or cobbled together Excel and point solutions.

Custom systems, built to match how a specific business actually operates, used to require a systems integrator: weeks of discovery, a proposal, a build. The discovery process itself, knowing which questions unlock the right configuration, is where most of that time and cost goes.

## The Approach

ERPForge is a set of Claude skills that encode a product consultant's discovery process, not a single ERP build:

- **`/design-review`** structured 10-section review before writing any code
- **Discovery templates** 80 questions across 12 categories for BOM and product scoping
- **`/write-docs`** auto-generates API reference, migration guides, and changelogs

The BOM rebuild on Sample ERP is where this got tested first. I gave Claude context on typical BOM structures and manufacturing processes, gave it the discovery skill, and had it interview me about product workflows and configurations. It rebuilt the data model from those answers. Four hours from kickoff to a restructured, production-ready BOM system, work that would normally take a systems integrator weeks.

The demo at erpforge.kyle-mcleod.io runs that discovery-to-spec flow directly: it interviews a user about their manufacturing operation and produces a structured spec and BOM configuration, the same judgment calls I made manually on Sample ERP, run through the skill instead of through me.

## What's Actually Hard

Encoding a consultant's judgment is slower than writing code. A good product consultant doesn't just ask questions, they know which questions unlock the right configuration, in what order, and how to translate the answer into an architecture decision. Getting explicit about knowledge that usually lives in someone's head, and reliable enough that Claude runs it consistently, is most of the actual work.

The demo proves the discovery-to-spec flow works. It doesn't yet close the loop into a build. That's the next milestone: full interview, build, and iteration without manual orchestration in between.

## What This Proves (So Far)

The discovery skill reliably turns a structured interview into a usable spec. That's phase one, and it's live now. It's the input side of the factory: turning a business's specific requirements into something a build can run on, without me in the loop translating.

Phase two is closing the loop: automating interview → build → iterate so the skill doesn't just produce a spec, it produces a working system. That's the difference between "I can build an ERP fast" and an actual software factory, where a product consultant's tooling can deliver a custom ERP to a manufacturer without the delivery time growing with each new customer. The bet is that the gap between "expert needed" and "anyone with domain knowledge can" keeps closing as the skills get better.
